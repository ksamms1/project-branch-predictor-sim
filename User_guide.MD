# USER GUIDE — Branch Predictor Simulator

# NOTE:
All instructions assume you are using the `feature/multi-program` branch.
This branch is the active development version and replaces main.

## What this program does

The simulator prints results to the console.
CSV files are generated by scripts in the scripts/ directory.

1. Single-program mode
- Runs one trace at a time
- Matches MP2 assignment behavior
- Produces baseline accuracy results

2. Multi-program mode
- Runs multiple traces simultaneously
- Uses one shared predictor
- Simulates interference between programs (trace files)
- Uses time-sliced round-robin scheduling

## Key Concept: Time Slice

Time `slice` = number of consecutive branches one program (i.e. trace) 
executes before the scheduler context switches to the next program in line.

# Example 1:
`slice` = 1
Program A: A1 A2 A3 A4 A5 ...
Program B: B1 B2 B3 B4 B5 ...
Program C: C1 C2 C3 C4 C5 ...

Program A executes 1 branch, then Program B's turn to execute 1 slice, then Program C, go back to A

A1 -> B1 -> C1 ==> A2 -> B2 -> C2 ==> A3 -> B3 -> C3 ==> A4 ...

# Example 2:
`slice` = 5
Program A executes 5 branches, then Program B executes 5 branches, then Program C executes 5 branches, go back to A

A1 A2 A3 A4 A5 -> B1 B2 B3 B4 B5 -> C1 C2 C3 C4 C5 ==> A6 A7 A8 A9 A10 -> B6 B7 ...

It is expected that realistic time slices will be slice = 5, slice = 100, slice = 1000, slice = 10,000, etc.

`Small slice` --> heavy interference/aliasing (history table thrashing)
`Medium slice` --> moderate interference
`Large slice` --> closer to single-program behavior (maybe predictor reaches steady state / best performance)

## Running the Simulator
The simulator prints results to the console only.
Use scripts in `scripts/` to generate CSV data.


# Single-program mode
```bash
./sim <predictor> <args> <tracefile>
```
# Examples:
```bash
./sim smith 3 traces/gcc_trace.txt
./sim bimodal 6 traces/jpeg_trace.txt
./sim gshare 9 3 traces/perl_trace.txt
./sim hybrid 8 14 10 5 traces/gcc_trace.txt
```


# Multi-program mode
```bash
./sim multi <slice> <predictor> <args> <trace1> <trace2> [trace3 ...]
```
# Examples:
```bash
./sim multi 1 smith 3 traces/gcc_trace.txt traces/jpeg_trace.txt

./sim multi 5 gshare 9 3 traces/gcc_trace.txt traces/jpeg_trace.txt

./sim multi 10 bimodal 6 traces/gcc_trace.txt traces/jpeg_trace.txt traces/perl_trace.txt

./sim multi 25 hybrid 8 14 10 5 traces/gcc_trace.txt traces/jpeg_trace.txt
```

# Explanation of `<args>` in `./sim multi <slice> <predictor> <args> <trace1> <trace2> ...`

- `<args>` comes from the predictor definition used in the MP2 assignment.

- smith `3`
  - `3` = number of bits in the single Smith saturating counter

- bimodal `6`
  - `6` = number of PC bits used to index into the bimodal prediction table of 3-bit counters

- gshare `9 3`
  - `9` = number of PC bits used for indexing
  - `3` = number of global branch history register bits XORed with the PC bits to form the final index into the prediction table of 3-bit counters

- hybrid `8 14 10 5`
  - `8` = number of chooser index bits used to index into the chooser table of 2-bit counters
  - `14` = number of PC bits used for indexing in the gshare predictor
  - `10` = number of global branch history register bits XORed with the selected PC bits in the gshare predictor
  - `5` = number of PC bits used to index into the bimodal predictor table

```bash

```
# Output:
```bash

```

# Multi-program experiments
```bash
./scripts/run_multi_experiments.sh
```
# Output:
```bash
results/multi_program_results.csv
```

## Output Files

### single_program_baselines.csv
- One row per (predictor, trace)
- Used as baseline for comparison

### multi_program_results.csv
- One row per program per run
- Includes:
  - slice size
  - predictor
  - trace combination
  - per-program stats
  - total stats

## What experiments this supports
- effect of time slice on prediction accuracy
- interference between programs
- comparison of predictors under contention
- degradation relative to baseline

## Important Notes
- Output format must not be modified without updating scripts
- Multi-program mode uses round-robin scheduling only
- No context-switch penalty is modeled

## Graphs
1. Misprediction Rate vs Time Slice
File: trace_set_rate_vs_slice.png
# What it shows:
- X-axis: time slice (number of branches executed before context switch) 
- Y-axis: misprediction rate (%) 
- Each line/point series: a trace set (e.g., gcc+jpeg, gcc+jpeg+perl) 
- Separate panels for each predictor 

# How to interpret it:
- Each point is a complete experiment run at that slice value 
- Smaller slices --> more frequent context switching --> more predictor interference 
- Larger slices --> behavior closer to single-program execution 
- Compare how different trace combinations affect predictor accuracy 

# Key takeaway:
- Shows how predictor accuracy changes as programs are interleaved more or less aggressively 

2. Degradation vs Time Slice
File: trace_set_degradation_vs_slice.png
# What it shows:
- X-axis: time slice 
- Y-axis: degradation = (multi-program rate − single-program baseline) 
- Each series: a trace set 
- Separate panels for each predictor 

# How to interpret it:
- Value = how much worse the predictor performs compared to running traces individually 
0 means no interference 
- Higher values mean more degradation due to sharing the predictor 

# Key takeaway:
- Directly measures interference caused by multi-program execution 
- Easier to compare across traces than raw misprediction rates 

3. Degradation Heatmap (All Trace Sets)
File: degradation_heatmap.png
# What it shows:
- X-axis: time slice (discrete tested values) 
- Y-axis: trace set (e.g., gcc+jpeg, gcc+jpeg+perl) 
- Color: degradation amount 

# How to interpret it:
- Each cell is one complete experiment 
- White ≈ no degradation 
- Red = higher degradation (worse performance) 
- Blue (if present) = better than baseline 

# Key takeaway:
- Quickly identifies: 
- worst-performing slice values 
- most problematic trace combinations 
- overall trends across predictors
